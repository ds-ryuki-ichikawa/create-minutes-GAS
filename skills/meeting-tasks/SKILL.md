# 議事録作成

Claude Code では、プラグインとして入れた場合は `/meeting-tasks:meeting-tasks`、スキルのフォルダをコピーして入れた場合は `/meeting-tasks` と入力すると実行する。Claude Desktop の Cowork では、`/` で出るメニューから `meeting-tasks` を選ぶか、議事録の作成を頼むと実行する。会議メモの URL がなくても、最近の会議メモを探して候補を出す。  
Google Docs の会議メモを読み込み、指定フォーマットで議事録・TODO を生成し、人が 1 回確認・承認したら、ローカル保存・Backlog 課題登録・Google カレンダーへのリマインド登録をまとめて行う。

引数: `$ARGUMENTS`

---

## 引数一覧

| 引数 | 必須 | 説明 |
|------|:----:|------|
| `--doc-id` | — | 会議メモ（Gemini によるメモ）の Google Docs ドキュメント ID または URL。省略時は最近の会議メモを探して候補を出す（Step 2） |
| `--memo-file` | — | パソコンにある会議メモのファイル（Markdown・テキスト）のパス。会議メモが手元にないときのお試し用（例: リポジトリの `samples/sample-meeting-memo.md`）。指定したときは Step 2 を飛ばし、Google ドライブを使わずに読み込む |
| `--backlog-project` | — | TODO を課題登録する Backlog プロジェクトキー。省略時は「設定の決め方」に従う（どこにもなければ確認の前に聞く） |
| `--save-folder` | — | 議事録を保存する Google ドライブのフォルダの URL または ID。省略時は「設定の決め方」に従う（どこにもなければパソコンのフォルダに保存する） |
| `--prev` | — | 前回の議事録。ローカルのファイルパス（`~/Documents/minutes/` 内ならファイル名だけでも可）または Google Docs の ID・URL。省略時は同じ名前の会議の議事録を自動で探す。`--prev none` で前回との比較をしない |
| `--dry-run` | — | お試し実行。保存・Backlog 登録・カレンダー登録は行わず、実行予定の内容を表示するだけにする |
| `--log` | — | テスト用。使った記録（確認・承認の時間、TODO の数、似た課題で止めた数）を残す（Step 13）。省略時は「設定の決め方」に従う（どこにもなければ記録しない） |

## 環境による違い

Claude Code（VS Code・ターミナル）と Claude Desktop の Cowork のどちらでも動くように書いている。違いは次の 4 点。

- **ツール名**: 手順に書いたツール名（`mcp__claude_ai_Google_Drive__read_file_content` など）は Claude Code での例。Cowork などでは名前が違うことがあるので、使えるツールの中から同じ機能のもの（Google ドライブのファイル検索・読み込み、Backlog の課題検索・登録、Google カレンダーの予定一覧・作成など）を選んで使う。引数名は各ツールの定義に合わせる
- **保存先フォルダ**: `SAVE_FOLDER`（「設定の決め方」を参照）が決まっていれば、議事録は Google ドライブのそのフォルダに保存する。どの環境でも同じ場所に残るので、以下の扱いは不要。決まっていない場合は、議事録は `~/Documents/minutes/` に保存する（以下 `MINUTES_DIR`）。Cowork では、接続されたフォルダのうち `minutes` フォルダ（またはドキュメントフォルダの中の `minutes`）を `MINUTES_DIR` とする。読み書きできるフォルダがない場合は、ユーザーに「ドキュメントの minutes フォルダを接続してください」と伝えてから進める。接続されなければ、議事録を Cowork の成果物ファイルとして出力し、その場所を保存先として報告する。claude.ai のチャットや Web 版 Claude Code（claude.ai/code）のようにクラウドで動く環境では、`~/Documents/minutes/` に書いてもユーザーのパソコンには保存されない。この場合は「パソコンには保存されません」とはっきり伝え、議事録をダウンロードできるファイルとして出す（出せなければ本文をコピーできる形で表示する）。お試し実行の保存予定の表示でも同じように伝える
- **Backlog**: Backlog のツールが使えない場合も処理を止めず、Step 7 の「Backlog が使えない場合」に従う。Backlog の接続は複数あることがある（例: プラグインに入っている `plugin:meeting-tasks:backlog` と、Claude Desktop の設定ファイルや拡張機能で入れた `backlog`）。どれかが「接続に失敗した」と通知されても、ほかの Backlog のツールがあればそれを使う。使えるかどうかは通知だけで決めず、Backlog のツール（例: スペース情報の取得）を実際に呼んで確かめる
- **答え方（ボタン）**: 「ユーザーへの聞き方」のとおり、選択肢を出すツールがある環境ではボタンで、ない環境では番号で答えてもらう

## ユーザーへの聞き方

ユーザーに選んでもらう場面（Step 2 の会議メモの選択、Step 8 の承認）では、次のように聞く。

- 選択肢を出すツール（例: Claude Code の `AskUserQuestion`）が使える場合は、それで聞く。選択肢は 2〜4 個にする（このツールは、選択肢のほかに自由に入力する欄を自動で付ける）
- 確認してほしい内容（一覧）は、ツールを呼ぶ前に本文に表示しておく。ボタンには短い名前しか出ないため
- ツールがない環境（Cowork・claude.ai など）では、本文の最後に選択肢を番号付きで書き（例: `1. 承認する　2. 修正する　3. やめる`）、番号か言葉での返事を待つ
- どちらの場合も、修正の指示（例: 「2 番の担当は佐藤さん」）はふつうの文章で受け付ける。ボタンで「修正する」が選ばれたら、「直したい内容を送ってください」と聞く

## 人の名前の書き方

議事録・TODO・Backlog の件名と詳細・カレンダーの予定に、お客様など社外の人や会社の名前を書くときは、必ず「様」を付ける（例: 山田様、A 社様）。会議メモに敬称がなくても付ける。

- 社内の人には敬称を付けない（議事録のふつうの書き方どおり、敬称略）
- Backlog の担当者の照合や、本人かどうかの判断では、敬称を外して比べる

## 設定の決め方

使う人や組織によって違う値は、次の順に探し、最初に見つかったものを使う。

| 変数 | 1. 引数 | 2. ユーザー設定 | 3. 組織の初期値 |
|------|---------|-----------------|-----------------|
| `BACKLOG_PROJECT`（Backlog のプロジェクトキー） | `--backlog-project` | `${user_config.backlog_project}` | `references/settings.md` の「Backlog のプロジェクトキー」 |
| `SAVE_FOLDER`（議事録を保存する Google ドライブのフォルダ） | `--save-folder` | `${user_config.save_folder}` | `references/settings.md` の「議事録の保存先」 |
| `LOG_RUN`（使った記録を残すか。テスト用） | `--log` | — | `references/settings.md` の「使った記録を残す」が「する」 |

- ユーザー設定は、Claude Code でプラグインとして入れ、設定画面で入力したときだけ値が入る。値が空のときや、ドル記号と波かっこで囲まれた `user_config` の文字のまま残っているときは、設定されていないとみなして次を見る
- 組織の初期値は、このスキルのフォルダにある `references/settings.md`（`${CLAUDE_SKILL_DIR}/references/settings.md`）に書く。値が空なら設定されていないとみなす
- `SAVE_FOLDER` が URL の場合は、`/folders/{ID}` の `{ID}` 部分を取り出す
- どこにもない場合、`BACKLOG_PROJECT` は空のままにして Step 7 でユーザーに聞く。`SAVE_FOLDER` は空のままにし、パソコンのフォルダに保存する
- Backlog の API キーは、引数や `references/settings.md` には書かない。Claude Code ではプラグインのユーザー設定に入れ（安全な保管場所に保存される）、Cowork では Claude Desktop の設定で Backlog の接続に入れる

## 実行手順

全体の流れ: 会議メモを決める（Step 1〜2）→ 読み込んで議事録を作る（Step 3〜5）→ 登録内容を準備する（Step 6〜7）→ **人が 1 回確認・承認する（Step 8）** → 保存・登録をまとめて行う（Step 9〜11）→ 完了報告（Step 12）→ 記録を残す（Step 13。テスト用で、`LOG_RUN` が true のときだけ）。人に聞くのは Step 8 の承認（と、必要なときの会議メモの選択・プロジェクトキー）だけにする。

### Step 1: 引数をパースする

引数（`$ARGUMENTS`）から以下を抽出し、各変数に格納する。引数が空の場合は、ユーザーのメッセージから読み取る（会議メモの URL が書かれていれば `--doc-id`、「お試し」とあれば `--dry-run` とみなす。会議名・日付・参加者の名前が書かれていれば、Step 2 で会議メモを探す手がかりにする）:

- `DOC_ID` ← `--doc-id` の値（URL の場合は `/document/d/{ID}/` の `{ID}` 部分を抽出する）。なければ空にし、Step 2 で決める
- `MEMO_FILE` ← `--memo-file` の値（なければ空）
- `BACKLOG_PROJECT` ← 「設定の決め方」に従う（`--backlog-project` → ユーザー設定 → 組織の初期値。どこにもなければ空）
- `SAVE_FOLDER` ← 「設定の決め方」に従う（`--save-folder` → ユーザー設定 → 組織の初期値。どこにもなければ空）
- `DRY_RUN` ← `--dry-run` が指定されていれば true、なければ false
- `LOG_RUN` ← `--log` が指定されているか、メッセージに「記録あり」とあれば true。なければ「設定の決め方」に従う（どこにもなければ false）
- `PREV_SOURCE` ← `--prev` の値（省略時は空文字＝自動で探す。`none` なら前回との比較をしない）

**`DRY_RUN` が true の場合:**  
Step 9 以降は外部・ファイルへの書き込みを一切行わず、各ステップで「実行予定の内容」を表示するだけにする。表示の先頭には `🧪 お試し実行（実際には保存・登録しません）` と出す。Step 8 の確認では、修正の練習ができるように、本番と同じく承認を待つ。

### Step 2: 会議メモを探す

`DOC_ID` と `MEMO_FILE` がどちらも空の場合だけ行う（URL かファイルが渡されていれば飛ばす）。

**1. 最近の会議メモを検索する**

Google ドライブのファイル検索ツール（例: `mcp__claude_ai_Google_Drive__search_files`）で探す。本文は不要で量も多いため、`excludeContentSnippets` は true にする。

- 基本の条件: `title contains 'Gemini によるメモ' and mimeType = 'application/vnd.google-apps.document' and createdTime > '{今日の 0:00（例: 2026-10-30T00:00:00+09:00）}'`
  - 議事録は会議が終わってすぐに作ることが多いため、まず今日の会議メモだけを探す
  - `mimeType` で Google ドキュメントだけに絞る。絞らないと、自分のドライブにある同じメモのショートカットも出てきて、候補が二重になる
- 今日の会議メモが 1 件もなければ、`createdTime` を 7 日前の 0:00 に広げてもう一度探す（前日の夕方の会議や、週明けにまとめて作る場合のため）
- ユーザーのメッセージに手がかりがあれば条件に足す:
  - 会議名 → `title contains '{会議名}'`
  - 参加者の名前 → `fullText contains '{名前}'`
  - 日付 → その日の 0:00 から翌日 0:00 までの `createdTime` の範囲（今日・7 日の条件は外す）
- 検索結果が複数ページに分かれて返る（次のページのトークンが付いている）ときは、最後のページまで取得する

**2. 候補を決める**

- 会議の日時の新しい順に並べ、上から 4 件を候補にする。会議の日時は、タイトルに日時（例: `2026/10/30 15:00`）があればそれを、なければ作成日時（JST）を使う
- 表示名は、タイトルから末尾の「 - Gemini によるメモ」と日時を除いたもの
- 候補ごとに Step 9 と同じ手順でファイル名（`{YYYY-MM-DD}_{sanitized_title}`）を作り、保存先（`SAVE_FOLDER` か `MINUTES_DIR`）に同じ名前の議事録がすでにあれば「（議事録あり）」と付ける

**3. どれで作るか聞く**

「ユーザーへの聞き方」に従い、候補を選択肢にして聞く。本文には次のように表示する:

```
📄 最近の会議メモ（どれで議事録を作りますか？）

  1. 10/30（金）15:00　定例会議
  2. 10/29（木）10:00　MTG（議事録あり）
  ...

ほかの会議なら、会議メモの URL か、会議名・日付を送ってください
```

- 選ばれた会議メモの ID を `DOC_ID` にして Step 3 へ進む
- URL が送られたらその ID を、会議名・日付が送られたらそれを手がかりに 1 から探し直す
- 候補が 1 件だけでも、勝手に始めずに「この会議メモで作りますか？」と確認する
- 見つからない場合は「最近の会議メモが見つかりませんでした。会議メモの URL か、会議名・日付を送ってください」と伝える
- Google ドライブのツールが使えない場合は、会議メモの URL を送ってもらう

### Step 3: 元ドキュメントを読み込む

Google ドライブのファイル読み込みツール（例: `mcp__claude_ai_Google_Drive__read_file_content`）の `fileId` に `DOC_ID` を渡してドキュメントを読み込む。  
ドキュメントのタイトルと本文全体を取得し、タイトルを `DOC_TITLE` に格納する。

- 本文には「メモ」タブ（概要・決定事項・次のステップ・詳細）と「文字起こし」タブの両方が含まれる
- `MEMO_FILE` がある場合は、Google ドライブを使わずにそのファイルを読み込む。1 行目をタイトル（`DOC_TITLE`）、残りを本文とする。ファイルが見つからなければ処理を中断し、パスを確かめるようユーザーに伝える。`DOC_ID` は空のままなので、Backlog の詳細とカレンダーの説明の「元メモ」の行は省く
- ファイルが見つからない・権限がない場合は処理を中断し、ドキュメントの共有設定を確認するようユーザーに伝える
- Google ドライブのツールが使えない場合は（`MEMO_FILE` がある場合を除き）処理を中断し、Google ドライブのコネクタを接続するようユーザーに伝える

### Step 4: 変換プロンプトを読み込む

このスキルのフォルダにある `references/minutes-template.md`（`${CLAUDE_SKILL_DIR}/references/minutes-template.md`）を読み込む。  
ファイルが見つからない場合は処理を中断し、スキルのファイル一式（`references/` フォルダを含む）がそろっているか確認するようユーザーに伝える。  
このファイルは議事録の生成方法を記述した変換プロンプトであり、Step 5 でそのまま指示として使用する。

### Step 4-2: 前回の議事録を読み込む

同じ会議の前回の議事録を読み込み、今回の議事録で「前回からの変更」を書けるようにする。`PREV_SOURCE` が `none` の場合はこのステップを飛ばし、`PREV_MINUTES` を空にする。

**1. 前回の議事録を見つける**

- `PREV_SOURCE` が Google Docs の ID・URL の場合: Step 3 と同じ Google ドライブのツールで読み込む
- `PREV_SOURCE` がファイルパスの場合: そのファイルを読み込む。ファイル名だけなら `MINUTES_DIR` から探す
- `PREV_SOURCE` が空の場合（自動で探す）:
  - `DOC_TITLE` から Step 9 と同じ手順で `sanitized_title` を作る
  - `SAVE_FOLDER` がある場合は、Google ドライブのファイル検索ツール（例: `mcp__claude_ai_Google_Drive__search_files`）で `parentId = '{SAVE_FOLDER}' and title contains '{sanitized_title}'` を検索し、タイトルが `{YYYY-MM-DD}_{sanitized_title}`（末尾に `_2`、`_3` … が付いたものも含む）のもののうち、日付が今回の会議日より前で最も新しいもの（同じ日付が複数あれば末尾の番号が大きいもの）を、Step 3 と同じツールで読み込む。検索結果が複数ページに分かれて返る（次のページのトークンが付いている）ときは、最後のページまで取得してから選ぶ。`PREV_FILE` にはそのファイルの URL を入れる
  - `SAVE_FOLDER` がない場合は、`MINUTES_DIR` から `{YYYY-MM-DD}_{sanitized_title}.md`（末尾に `_2`、`_3` … が付いたものも含む）を探し、日付が今回の会議日より前のものの中で最も新しいものを選ぶ（同じ日付が複数あれば末尾の番号が大きいもの）
- 見つからない・読み込めない場合は処理を止めずに `PREV_MINUTES` を空にし、「前回の議事録は見つかりませんでした（初回の会議として扱います）」と表示する
- 見つかった場合は、本文を `PREV_MINUTES`、ファイルの場所を `PREV_FILE`、前回の開催日を `PREV_DATE` に格納し、「📎 前回の議事録：{PREV_FILE}（{PREV_DATE}）と比べます」と表示する

**2. 前回の TODO の Backlog の状態を調べる**

`PREV_MINUTES` が空でない場合、前回の TODO を登録した Backlog の課題を探す。

- Backlog の課題検索ツール（例: `mcp__backlog__get_issues`）で、`keyword` に前回の会議名（`PREV_MINUTES` のタイトル行から「 議事録」を除いたもの）、`count` に 20 を指定して検索する
- 説明文に `開催日: {PREV_DATE}` を含む課題だけを、前回の TODO の課題とみなす
- 課題キー・件名・状態を `PREV_BACKLOG` に格納する。見つからなければ空にする（前回 Backlog に登録していない場合もある）
- Backlog のツールが使えない場合は `PREV_BACKLOG` を空にして先に進む（前回の TODO の状況は会議での発言だけで判断する）

### Step 5: 議事録を Markdown で生成する

Step 3 で取得した元ドキュメントの本文を入力として、Step 4 で読み込んだ変換プロンプトの指示に従って議事録を Markdown で生成する。`PREV_MINUTES` が空でない場合は、`PREV_MINUTES` と `PREV_BACKLOG` も「前回の議事録」「前回の TODO の Backlog の状態」として渡す。

変換プロンプトに記載のない点については以下のデフォルトルールを適用する:
- 箇条書きを積極活用し、読みやすく簡潔にまとめる
- 会議日時・参加者は変換プロンプトの「会議情報」に記載するため、ここでは重複して書かない
- 議事録の冒頭に以下のタイトル行を挿入する（`DOC_TITLE` 末尾の「 - Gemini によるメモ」は除く）:

```
# {DOC_TITLE} 議事録

**作成日**: {今日の日付 YYYY-MM-DD}
```

生成した結果を、区切りの行（`<!-- ここから下は確認用のメモ（議事録には載せない） -->`）で 2 つに分ける。区切りより上（議事録の本文）を `MINUTES_MD` に、下（非公開情報・要確認事項）を `CHECK_NOTES` に格納する。区切りの行はどちらにも含めない。`CHECK_NOTES` は Step 8 の確認の画面だけで使い、保存する議事録には入れない。

### Step 6: TODO を抽出する

`MINUTES_MD` の「TODO」セクションの内容を、確認と Backlog 登録で使うために以下の Markdown テーブルに整形する。  
`TODO_MD` は議事録本文（保存するファイル）には追加しない（`MINUTES_MD` に TODO が既に含まれるため）:

```markdown
## TODO一覧

| 対応フラグ | 対応内容 | 区分 | 担当者 | 期限 |
|-----------|---------|------|--------|------|
| [ ] | {内容} | {社内・社外・不明} | {担当者名または「未定」} | {期限（YYYY-MM-DD）または「未定」} |
```

- `MINUTES_MD` の TODO の表の「誰が」を担当者、「何を」を対応内容、「いつまで」を期限として使う
- 担当者名はドキュメント本文から判断する（記載がなければ「未定」）
- 区分は `MINUTES_MD` の「TODO」セクションの区分をそのまま使う
- 期限は `YYYY-MM-DD` 形式。「次回MTGまで」「月末」など相対表現は可能な範囲で日付化する
- TODO が 0 件の場合は「*TODOなし*」と記載する

抽出した Markdown テーブルを `TODO_MD` に、件数を `TODO_COUNT` に格納する。

### Step 7: 登録内容を準備する

Step 8 で保存・登録の内容をまとめて確認できるように、Backlog とカレンダーに登録する内容を先に組み立てる。このステップでは何も登録しない。

#### 7-1. Backlog に登録する課題

`TODO_MD` のうち区分が「社内」の行を、`BACKLOG_PROJECT` の課題として登録する対象にする。社内の TODO が 0 件なら、Backlog の準備は飛ばす。

`BACKLOG_PROJECT` が空の場合は、Step 8 の前に「どの Backlog プロジェクトに登録しますか？（プロジェクトキー）」と聞き、答えを `BACKLOG_PROJECT` に入れる。`DRY_RUN` が true の場合は聞かずに、プロジェクト名を「（プロジェクト未設定）」として進める。

- 区分が「社外」の行（お客様・取引先の作業）は社内の Backlog に登録しない。確認の画面で「登録しない（社外の作業）」と表示する
- 区分が「不明」の行は ⚠ を付けて確認の画面に出し、登録するかどうかをユーザーに決めてもらう（指示がなければ登録しない）
- 「（前回から継続）」の行で、`PREV_BACKLOG` に対応する課題がある場合は新しく登録しない。確認の画面に「前回の課題を継続：{課題キー}（{状態}）」と表示し、期限が変わった場合は課題の期限の更新を提案する（更新はユーザーが指示したときだけ行う）

**Backlog が使えない場合:**  
Backlog のツールが使えない（コネクタ未接続・未認可。「環境による違い」のとおり、実際に呼んで確かめる）場合は処理を中断せず、`BACKLOG_AVAILABLE` を false にする。担当者の照合と似た課題の確認はせず、確認の画面で「Backlog に手で登録（未接続）」と表示する。承認後に Step 10 で手動登録用の一覧を出す。

**登録内容を組み立てる:**

- プロジェクト・ユーザー・種別・優先度は、Backlog のプロジェクト・プロジェクトユーザー・種別・優先度の取得ツール（例: `mcp__backlog__get_project`、`mcp__backlog__get_project_users`、`mcp__backlog__get_issue_types`、`mcp__backlog__get_priorities`）で取得する
- 件名: TODO の「対応内容」
- 種別: 「タスク」、優先度: 「中」
- 担当者: TODO の担当者名とプロジェクトユーザーの `name` を、半角・全角スペースと敬称（さん・様）を無視して照合する
  - 1 人に一致 → その人を担当者にする
  - 一致なし、または名字だけで複数人に一致 → 担当者は空にし、⚠ を付けて確認対象にする
- 期限: TODO の期限（`YYYY-MM-DD`）。「未定」なら設定しない
- 重複確認: TODO の内容から主な語句（例: 「注文メール」「取り込み」）を選び、Backlog の課題検索ツール（例: `mcp__backlog__get_issues`）の `keyword` で `BACKLOG_PROJECT` の課題を検索する。完了済みも含めて、同じ作業と思われる課題があれば、その課題キー・件名・状態を控えて確認対象にする。検索結果には課題の説明文がまるごと含まれて量が多くなるため、語句は TODO 全体で 3〜4 個までに絞り（1 つの語句で複数の TODO をまとめて確かめる）、`count` は 10 にする
- 詳細: 以下の形式

```
会議: {DOC_TITLE（「 - Gemini によるメモ」を除く）}
開催日: {会議日付}
元メモ: https://docs.google.com/document/d/{DOC_ID}/edit
（meeting-tasks により自動登録）
```

#### 7-2. カレンダーに入れるリマインド

Backlog に登録する対象にした社内の TODO のうち、期限が決まっているものについて、実行者の Google カレンダーに入れるリマインドの予定を組み立てる。期限が「未定」の TODO と社外の TODO は対象外（社外の期限もリマインドしたい場合は、確認時にユーザーが追加を指示する）。期限が今日より前の TODO も、リマインドにならないので入れない。確認の画面で「期限が過ぎている」と知らせる（それでも入れたい場合は、ユーザーが指示する）。対象が 0 件なら、カレンダーの準備は飛ばす。

**Google Calendar が使えない場合:**  
Google Calendar のツールが使えない（コネクタ未接続・未認可）場合は処理を中断せず、`CALENDAR_AVAILABLE` を false にする。確認の画面で「カレンダーに手で登録（未接続）」と表示し、承認後に Step 11 で手動登録用の一覧を出す。

**予定の内容を組み立てる:**

- 予定の種類: 期限日の終日予定（終了日は期限日の翌日を指定する）
- タイトル: `【期限】{対応内容}`
- 通知: ポップアップ通知を開始の 900 分前に設定する（期限の前日 9:00 JST に鳴る）
- 説明: 以下の形式（Backlog の URL は Step 10 で登録したあとに入れる）

```
担当者: {担当者名または「未定」}
会議: {DOC_TITLE（「 - Gemini によるメモ」を除く）}
Backlog: {Step 10 で登録した課題の URL。登録していなければ省く}
元メモ: https://docs.google.com/document/d/{DOC_ID}/edit
（meeting-tasks により自動登録）
```

- 招待: TODO の担当者を、メールアドレスがわかる場合だけ招待する
  - Backlog では他のユーザーのメールアドレスを取得できない（本人のものしか見えない）ため、担当者のメールアドレスは確認時にユーザーから受け取る
  - 担当者が実行者本人の場合は招待しない。本人かどうかは、予定を作るカレンダーの持ち主（自分）のメールアドレスと比べて判断する。会議の招待者情報などから担当者のアドレスがわかっても、それが自分のアドレスなら招待しない
  - 自分のメールアドレスは、招待する人を決める前に、Google カレンダーのカレンダー一覧ツール（例: `mcp__claude_ai_Google_Calendar__list_calendars`）で確かめる。自分のメインのカレンダーの ID（メールアドレスの形のもの。祝日などのカレンダーは除く）が自分のメールアドレス。お試し実行でも同じように確かめ、自分のアドレスは招待の欄に出さない
  - メールアドレスがわからない担当者（自分以外）は招待せず、⚠ を付けて確認対象にする
- 重複防止: Google カレンダーの予定一覧ツール（例: `mcp__claude_ai_Google_Calendar__list_events`）で期限日（`startTime`: 期限日 `T00:00:00`、`endTime`: 翌日 `T00:00:00`、`fullText`: `【期限】`）の予定を取得し、同じタイトルの予定がすでにある場合は作らず、「登録済み」として扱う

#### 7-3. 保存するファイル名

Step 9 の手順で、議事録を保存するファイル名と場所を決めておく（まだ保存はしない）。`SAVE_FOLDER` があれば Google ドライブのそのフォルダ、なければ `MINUTES_DIR`。

### Step 8: まとめて確認・承認してもらう

議事録の内容と、保存・登録する内容を 1 つの画面にまとめて表示し、承認を 1 回だけもらう。表示の形式:

```
📋 内容を確認してください（承認すると、議事録の保存と Backlog・カレンダーへの登録をまとめて行います）

■ TODO と登録先（Backlog：{BACKLOG_PROJECT}）
  1. [{区分}] {内容}｜{担当者}｜{期限} → {登録先}
     {必要なときだけ、注意を 1 行ずつ}
  ...

■ 議事録の保存先
  {保存先のフォルダ}/{ファイル名}

■ 非公開情報（社外に共有する前に伏せるか確認）
  {CHECK_NOTES の「非公開情報」の内容}

■ 前回からの変更（前回：{PREV_DATE}｜{PREV_FILE}）
  {MINUTES_MD の「前回からの変更」の内容。前回の議事録がない場合は「前回の議事録なし（初回として扱いました）」}

■ 要確認事項
  {CHECK_NOTES の「要確認事項」の内容}
  {要確認事項が残っている場合: ※ 残ったまま承認すると、議事録の「決まっていないこと」に入れて保存します}
```

- `{登録先}` は次のどれか: 「Backlog・カレンダー」「Backlog だけ（期限がないためカレンダーには入れない）」「Backlog だけ（⚠ 期限が過ぎているためカレンダーには入れない）」「登録しない（社外の作業）」「⚠ 区分が不明（社内の作業なら登録します）」「前回の課題を継続：{課題キー}（{状態}）」。Backlog・カレンダーが使えない場合は「Backlog に手で登録（未接続）」のように書く
- 注意の行の例: 「⚠ 似た課題あり：{課題キー}「{件名}」（{状態}）。登録すると重複するおそれ」「⚠ Backlog の担当者が見つからない（{担当者名}）」「⚠ カレンダーに招待しない（{担当者名}のメールアドレスが不明）」
- 担当者または期限が「未定」、区分が「不明」の項目には、行の先頭に ⚠ を付ける
- 表示したら、「ユーザーへの聞き方」に従って、次の 3 つから選んでもらう。ボタンがない環境では、最後に「1. 承認する　2. 修正する（直したい内容を送ってください）　3. やめる」と書く
  - **承認する**: 保存・登録まで進める
  - **修正する**: 直したい内容を送ってもらう
  - **やめる**: 何も保存・登録せずに終える（「何も保存・登録していません」と伝える）
- 承認を受けるまで、Step 9 以降（保存・登録）は実行しない。「OK」「登録」「承認」も承認として扱う
- 修正の指示（例: 「2 番の担当は佐藤さん」「3 番は Backlog に入れない」「8 番の招待は sato@example.com」）を受けたら、`MINUTES_MD`・`CHECK_NOTES`・`TODO_MD`・登録内容に反映し、変更点（変更前 → 変更後）を表示してから、もう一度この画面を表示する。担当者や期限が変わったら、Step 7 の照合・重複確認もやり直す
- 反映して解消した要確認事項は `CHECK_NOTES` から消す
- 要確認事項が残ったまま承認された場合は、聞き直さずに、残った項目を `MINUTES_MD` の「決まっていないこと」に足してから Step 9 へ進む（各項目の末尾に「（要確認）」を付ける。「なし」と書いてあれば置き換える）。画面に「残ったまま承認すると、決まっていないことに入れて保存します」と書いてあるため、承認のあとに確認を足さない（人の操作を承認 1 回にするため）
- `DRY_RUN` が true の場合も、ここでは承認を待つ。承認されたら、Step 9 以降は実行予定の内容を表示するだけにする
- `LOG_RUN` が true の場合だけ、`references/run-log.md` の「Step 8 で控えること」に従って、時刻などを控える

### Step 9: 議事録を保存する

Step 8 で承認を受けた確定版を保存する。`SAVE_FOLDER` があれば Google ドライブに、なければ `MINUTES_DIR`（「環境による違い」を参照）に保存する。ファイル名はどちらも下の 2 の手順で作る。

**`SAVE_FOLDER` がある場合（Google ドライブに保存）:**

- 同じフォルダに同じ名前のファイルがあるか、Google ドライブのファイル検索ツールで確かめる。検索結果が複数ページに分かれて返るときは、最後のページまで取得する（Google ドライブは同じ名前のファイルを作れてしまうため、見落とすと重複する）。あれば上書きせず、末尾に `_2`、`_3` …を付けて空いている名前にする（Google ドライブでは拡張子 `.md` は付けない）
- Google ドライブのファイル作成ツール（例: `mcp__claude_ai_Google_Drive__create_file`）で、`parentId` に `SAVE_FOLDER`、`title` にファイル名、`textContent` に `MINUTES_MD`、`contentMimeType` に `text/markdown` を指定して作る（Google ドキュメントに変換される）
- 作ったファイルの URL（`https://docs.google.com/document/d/{ID}/edit`）を `LOCAL_FILE_PATH` に格納する
- フォルダが見つからない・書き込めない場合は、処理を止めてユーザーに伝え、パソコンのフォルダに保存するか聞く

**`SAVE_FOLDER` がない場合（パソコンのフォルダに保存）:**

1. `MINUTES_DIR` が存在しない場合は作成する（例: PowerShell なら `New-Item -ItemType Directory -Force "$env:USERPROFILE\Documents\minutes"`、bash なら `mkdir -p ~/Documents/minutes`）
2. ファイル名: `{YYYY-MM-DD}_{sanitized_title}.md`（`YYYY-MM-DD` は会議日付）。日付はファイル名の先頭に 1 回だけ付ける。`sanitized_title` は `DOC_TITLE` から以下の順に作る:
   - 末尾の「 - Gemini によるメモ」を除く
   - 日付（例: `2026/10/02`、`2026-10-02`、`20261002`、`10/2`）、時刻（例: `14:29`）、タイムゾーン（例: `JST`）を除く
   - 空白・記号をアンダースコアに置換し、連続・先頭・末尾のアンダースコアを整理する
   - 結果が空になった場合は「会議」とする
   - 例: `MTG - 2026/10/02 14:29 JST - Gemini によるメモ` → `2026-10-02_MTG.md`
3. 同名ファイルが既に存在する場合は上書きせず、末尾に `_2`、`_3` …を付けて空いている名前で保存する
4. `MINUTES_MD`（議事録本文）をファイルに保存する
5. 保存先の絶対パスを `LOCAL_FILE_PATH` に格納する

### Step 10: Backlog に課題を登録する

Step 8 で承認された内容のとおり、Step 7-1 で組み立てた課題を登録する。ここではもう確認を求めない。対象が 0 件の場合はこのステップを飛ばす。

Backlog の課題登録ツール（例: `mcp__backlog__add_issue`）で 1 件ずつ登録する。作成された課題キーと URL（`https://{スペースキー}.backlog.jp/view/{課題キー}`。スペースキーはスペース情報の取得ツール（例: `mcp__backlog__get_space`）で取得する）を `BACKLOG_ISSUES` に、件数を `BACKLOG_COUNT` に格納する。  
途中で失敗した場合は、そこで止めて登録済みの課題キーと失敗した TODO をユーザーに伝える。  
登録した課題は権限によっては削除できないため、不要になった課題はコメントを付けてクローズするか、管理者に削除を依頼するようユーザーに伝える。

**Backlog が使えない場合（`BACKLOG_AVAILABLE` が false）:**  
課題は作らず、Step 12 で「未登録：手動登録用の一覧を表示済み」と報告し、以下の一覧を表示する:

```
📝 Backlog が接続されていないため、以下を {BACKLOG_PROJECT} に手動で登録してください

  1. {件名}｜担当：{担当者}｜期限：{期限 または なし}
  ...

  登録しない TODO（社外の作業）：
  - {内容}｜{担当者}｜{期限}
```

### Step 11: Google カレンダーにリマインドを登録する

Step 8 で承認された内容のとおり、Step 7-2 で組み立てた予定を作る。ここではもう確認を求めない。対象が 0 件の場合はこのステップを飛ばす。

Google カレンダーの予定作成ツール（例: `mcp__claude_ai_Google_Calendar__create_event`）で 1 件ずつ登録し、件数を `CALENDAR_COUNT` に格納する。説明の `Backlog:` には、Step 10 で登録した課題の URL を入れる。以下は Claude Code のツールの引数名で、ほかの環境では各ツールの定義に合わせる:
- `summary`: タイトル
- `allDay`: true
- `startTime`: 期限日 `T00:00:00`（例: `2026-10-30T00:00:00`）、`endTime`: 翌日 `T00:00:00`
- `overrideReminders`: `[{"method": "popup", "minutes": 900}]`
- `availability`: `AVAILABILITY_FREE`（リマインドなので、予定の空き状況をふさがない）
- `description`: 説明
- `attendees`: 招待する人の `email`（いなければ省く）

途中で失敗した場合は、そこで止めて登録済みの予定と失敗した TODO をユーザーに伝える。

**Google Calendar が使えない場合（`CALENDAR_AVAILABLE` が false）:**  
予定は作らず、Step 12 で「未登録：手動登録用の一覧を表示済み」と報告し、以下の一覧を表示する:

```
📅 Google Calendar が接続されていないため、以下を手動でカレンダーに登録してください

  1. {期限}（終日）【期限】{対応内容}｜担当：{担当者}
  ...
```

### Step 12: 完了報告

以下をまとめて出力する:

```
✅ 議事録作成完了

📄 保存先         : {LOCAL_FILE_PATH}（Google ドライブに保存した場合はその URL。クラウドで動く環境でパソコンに保存しようとした場合は「パソコンには未保存：ダウンロード用のファイルを表示済み」）
📝 Backlog 課題   : {BACKLOG_COUNT} 件登録（{課題キーをカンマ区切り}）（Backlog が使えない場合は「未登録：手動登録用の一覧を表示済み」）
📅 カレンダー     : {CALENDAR_COUNT} 件のリマインドを登録（Google Calendar が使えない場合は「未登録：手動登録用の一覧を表示済み」）
✅ TODO           : {TODO_COUNT} 件抽出（社内 {社内の件数} 件・社外 {社外の件数} 件・不明 {不明の件数} 件。不明が 0 件なら「・不明」以降は省く）
🔗 前回の議事録   : {PREV_FILE}（{PREV_DATE}）と比較（前回の議事録がない場合は「なし」）
```

### Step 13: 記録を残す（テスト用）

`LOG_RUN` が true の場合だけ行う。false なら何もしない。

`references/run-log.md`（`${CLAUDE_SKILL_DIR}/references/run-log.md`）を読み込み、その「Step 12 で足すこと」と「記録を残す」に従う。「やめる」が選ばれたときも、記録だけを残す。
